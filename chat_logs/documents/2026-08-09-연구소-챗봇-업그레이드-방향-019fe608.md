## 가장 먼저 만들 기능

### 1. 자연어 검사항목 검색

SCL은 [검사항목조회](https://www.scllab.co.kr/front/check/check_item_list.do)에 3,300개 이상의 검사가 있고, 검사코드·검체·검사방법·검사일·소요일 등의 구조화된 정보가 있습니다. 이것이 챗봇의 가장 강력한 기반입니다.

예를 들면:

> “알츠하이머를 혈액으로 검사할 수 있나요?”  
> “β2-microglobulin 검사할 때 어떤 검체가 필요한가요?”  
> “검사코드는 모르는데 대변으로 하는 염증검사 찾아줘.”  
> “금요일에 검체를 보내면 결과가 언제 나오나요?”

챗봇은 다음을 한 번에 보여주는 방식이 좋습니다.

- 추천 또는 일치하는 검사항목
- 검사코드와 보험코드
- 검체 종류, 용기, 필요량
- 보관·운송 방법
- 검사 가능 요일과 예상 소요일
- 상세페이지·의뢰서 바로가기
- 정보 기준일과 출처

검사명이 정확하지 않아도 동의어, 약어, 한글·영문 혼용을 이해해야 합니다.

### 2. 검체 채취·보관 도우미

연구소에서 전화 문의를 가장 많이 줄일 가능성이 큰 기능입니다.

> “CBC 검체 냉장 보관해도 되나요?”  
> “혈청이 용혈됐는데 검사할 수 있나요?”  
> “24시간 소변 검사 용기와 보존제가 궁금해요.”  
> “검체량이 부족한데 가능한가요?”

다만 검사별 공식 지침을 근거로 답해야 하며, 확실하지 않으면 추측하지 않고 담당 부서로 연결해야 합니다.

### 3. 업무처리 내비게이터

현재 버튼형 챗봇의 기능을 자연어로 바꿉니다.

> “환자 생년월일을 잘못 입력했어요.”  
> “의뢰한 검사 하나를 취소하고 싶어요.”  
> “EMR 연동이 안 됩니다.”  
> “지난달 거래명세서가 필요해요.”

챗봇이 필요한 정보를 순서대로 물은 뒤:

- 적절한 신청 화면으로 이동
- 담당 부서와 연락처 안내
- 문의 내용을 정리해 상담원에게 전달
- 로그인 사용자라면 처리 상태 조회

까지 연결할 수 있습니다. 실제 취소·정보수정처럼 중요한 작업은 본인확인과 최종 확인 후 기존 시스템 API로 처리해야 합니다.

### 4. 공문·일정 안내

[SCL 메인 사이트](https://www.scllab.co.kr/front/main.do)에 검사 변경, 신규검사, 연휴 일정 등의 공문이 계속 올라오므로 자연어 검색 효과가 큽니다.

> “광복절 연휴에 검사 일정이 어떻게 바뀌나요?”  
> “최근 중단된 검사가 있나요?”  
> “MAST 신규검사 변경사항만 요약해줘.”

답변에는 반드시 공문 날짜와 원문 링크를 함께 보여줘야 오래된 정보로 잘못 안내하는 문제를 막을 수 있습니다.

### 5. 연구·사업 문의 상담

임상시험, 인체유래물은행, IRB, 연구용 검사 문의를 분류하고 상담에 필요한 정보를 미리 수집합니다.

예를 들어 연구 목적, 검체 종류, 예상 건수, 필요 검사법, 일정, 담당자 연락처를 받아 담당 부서에 구조화된 형태로 넘기면 단순한 FAQ보다 사업적인 가치도 생깁니다.

## 추천하는 서비스 구조

챗봇을 두 영역으로 나누는 것이 안전합니다.

| 공개 챗봇 | 로그인 후 업무 챗봇 |
|---|---|
| 검사항목 검색 | 검사 진행상태 조회 |
| 검체·용기·보관 안내 | 검사 추가·취소 신청 |
| 공문 및 일정 검색 | 환자정보 수정 요청 |
| 부서·지역센터 안내 | 거래명세서·계정 문의 |
| 연구·사업 문의 접수 | EMR 및 원격지원 연결 |

환자정보나 검사결과는 로그인 전에는 절대 다루지 않아야 합니다. 결과의 의학적 해석도 일반 사용자에게 진단처럼 제공하지 않고 의료진 상담으로 안내하는 편이 안전합니다.

## 기술적으로는 이렇게 가는 게 좋습니다

핵심은 단순한 ChatGPT 연결이 아니라 다음의 조합입니다.

```text
사용자 자연어
    ↓
질문·사용자 유형 파악
    ↓
SCL 공식 데이터 검색
(검사항목 DB·공문·매뉴얼·FAQ)
    ↓
근거가 있는 답변 생성
    ↓
필요하면 기존 업무 시스템/API 실행
    ↓
불확실하거나 예외적인 경우 상담원 연결
```

검사정보는 자주 변경되므로 모델 자체에 외우게 하는 파인튜닝보다, **현재 검사 DB와 문서를 실시간으로 조회하는 RAG 방식**이 우선입니다. 취소·수정·조회는 생성형 AI가 임의로 처리하지 않고 정해진 API와 업무 규칙을 사용해야 합니다.

## 현실적인 도입 순서

1단계에서는 기존 챗봇을 버리지 말고 자연어 입력창을 추가합니다. 검사항목, 검체 안내, 공문, FAQ 검색에 집중하고 답변 아래에는 기존 버튼을 보조 선택지로 유지합니다.

2단계에서는 로그인과 상담 시스템을 연결해 검사 추가·취소, 전산 문의, 거래명세서 등의 접수 과정을 자동화합니다.

3단계에서는 실제 질문 로그를 분석해 답변하지 못한 질문, 전화로 전환된 질문, 잘못 검색된 검사명을 지속적으로 개선합니다.

## 성공 여부를 판단할 지표

- 사용자가 재질문 없이 해결한 비율
- 상담원·전화로 넘어간 비율
- 검사항목 검색 성공률
- 평균 해결 시간
- 상담원에게 전달되는 문의정보의 완성도
- 근거 없는 답변 발생률
- 개인정보·의료안전 사고 건수

가장 추천하는 첫 MVP는 **“자연어 검사항목 검색 + 검체 채취 안내 + 공문 검색 + 상담원 연결”**입니다. 이 네 가지면 생성형 AI의 장점을 보여주면서도 개인정보와 의료적 위험을 비교적 낮게 관리할 수 있습니다. 버튼은 없애는 대상이 아니라, 자연어 답변의 다음 행동을 확정하는 안전장치로 남기는 것이 좋습니다.

## 가장 먼저 확인하고 싶은 것

### 1. 누가 주 사용자야?

이게 가장 중요해.

- 병·의원 간호사나 검사 담당자
- 의사
- 일반 환자
- 연구자·제약회사
- SCL 내부 직원

사용자에 따라 질문과 답변 수준이 완전히 달라져.

예를 들어 병원 담당자는 “검체 용기와 소요일”을 묻지만, 일반 환자는 “이 검사로 암인지 알 수 있나요?”라고 물을 수 있어. 후자는 의료적 진단 문제까지 생겨.

내 예상으로는 **병·의원 실무자를 1순위 사용자로 잡는 것**이 가장 현실적이야. 맞아?

### 2. 챗봇이 어디까지 ‘처리’해야 해?

자연어 답변만 제공하는 것과 실제 업무까지 수행하는 것은 난도가 크게 달라.

예를 들어:

- “검사 취소는 여기에서 하세요”라고 안내
- 검사 취소 요청을 접수
- 로그인 후 실제 검사 취소 처리

이 셋은 전혀 다른 서비스야.

회사가 말하는 “단순 링크 이동밖에 못 한다”는 단점 때문에, 최소한 **필요한 정보를 받아 문의를 접수하거나 담당자에게 전달하는 수준**까지는 기대할 가능성이 커 보여.

### 3. 1차 출시에서 답변할 질문 범위는 어디까지야?

기존 챗봇에는 다음 문의가 있어.

- 검체 채취 및 주의사항
- 검사 의뢰서
- 검사 추가·취소
- 환자정보 수정
- 연구용 검사
- 특수검진·건강검진
- 계정·비밀번호
- EMR·전산
- 세금계산서·거래명세서
- 채용·재직
- 자주 묻는 질문

모든 영역을 처음부터 자연어로 처리할지, 우선순위를 정할지 결정해야 해.

내 추천 MVP 우선순위는:

1. 검사항목 자연어 검색
2. 검체·용기·채취·보관 안내
3. 검사일·소요일·일정 안내
4. 공문 및 변경사항 검색
5. 문의 분류와 담당 부서 연결

검사 취소나 환자정보 변경처럼 시스템 연동이 필요한 기능은 2단계가 적절해 보여.

### 4. 검사결과 해석도 해줘야 해?

이건 반드시 경계를 정해야 해.

예를 들어:

> “AST 수치가 80인데 간이 안 좋은 건가요?”

이런 질문에 챗봇이 답하게 할지, 검사정보만 제공하고 의료진 상담으로 돌릴지 결정해야 해.

나는 다음 원칙을 추천해.

- 검사 목적과 일반적인 정보: 답변 가능
- 검사결과 조회: 로그인·권한 확인 후 가능
- 개인 검사결과 해석 및 진단: 제공하지 않음
- 응급하거나 위험한 의료질문: 의료기관 안내
- 불확실한 검사정보: 추측하지 않고 상담원 연결

### 5. RAG에 사용할 공식 데이터는 무엇이야?

실서비스 가능성을 결정하는 질문이야.

필요한 데이터 후보는:

- 검사항목 DB
- 검사코드·보험코드
- 검체·용기·필요량
- 채취·보관·운송 방법
- 검사일·소요일
- 검사의뢰서
- 공문·신규검사 안내
- FAQ
- 업무 매뉴얼
- 지역센터·담당부서 정보
- 기존 상담 내역 또는 전화 문의 유형

특히 검사항목 DB를 직접 조회할 수 있는 API가 있는지, 홈페이지를 크롤링해야 하는지, DB 접근 권한을 받을 수 있는지가 궁금해.

### 6. 답변의 최신성을 누가 관리해?

RAG를 사용한다고 자동으로 최신 정보가 보장되지는 않아.

확인해야 할 것은:

- 검사정보는 얼마나 자주 변경되는가?
- 공문 등록 즉시 챗봇에 반영해야 하는가?
- 잘못된 문서를 누가 수정하는가?
- 답변에 출처와 기준일을 보여줄 것인가?
- 문서가 서로 충돌하면 무엇을 우선하는가?

나는 모든 검사 답변에 다음을 표시하는 방향을 추천해.

> 정보 기준일, 참조 문서, 검사 상세보기, 확실하지 않을 때 문의처

### 7. 개인정보를 챗봇에 입력해도 되는가?

사용자가 다음을 입력할 가능성이 높아.

- 환자 이름
- 생년월일
- 병원명
- 검체번호
- 검사결과
- 전화번호
- 이메일

따라서 공개 챗봇과 로그인 챗봇을 분리할지, 개인정보 입력을 탐지해 차단할지, 대화 로그를 저장할지 결정해야 해.

### 8. 상담원 연결은 어떻게 할 거야?

챗봇이 모르는 질문은 반드시 사람이 이어받아야 해.

- 전화번호만 안내
- 1:1 문의 작성
- 실시간 상담원 연결
- 담당 부서에 티켓 생성
- 대화 내용을 요약해서 전달

“다시 처음부터 설명해야 하는 불편”을 없애려면 마지막 방식이 가장 좋아.

## 성공 기준도 우선순위를 정해야 해

“전부 다”는 목표로는 맞지만 평가 기준으로는 부족해. 다음처럼 나누는 것이 좋아.

### 핵심 성과

- 전화 문의 감소
- 챗봇 내 문제 해결률
- 검사항목 검색 성공률

### 보조 성과

- 검사 검색 시간 감소
- 홈페이지 이탈률 감소
- 답변 가능 질문 범위 증가
- 사용자 만족도

### 반드시 지켜야 할 품질 기준

- 검사정보 정확도
- 답변 출처 제시율
- 개인정보 노출 건수
- 근거 없는 답변 발생률
- 위험한 의료 답변 발생 건수

즉, 단순히 많이 답변하는 것이 성공이 아니라 **정확하게 해결하면서 위험한 질문에는 답하지 않는 것**까지 포함해야 해.

가장 먼저 결정해야 할 것은 다음 세 가지야.

1. 주 사용자가 병·의원 실무자인가?
2. 챗봇이 안내만 하는가, 실제 접수·처리까지 하는가?
3. 개인 검사결과 해석은 범위에서 제외하는가?

이 세 가지가 정해지면 챗봇의 핵심 기능, 데이터, 화면 흐름, 아키텍처까지 상당히 구체적으로 설계할 수 있어.

# SCL 자연어 챗봇 기획안 v0.1

## 1. 과제 정의

> 기존 버튼형 챗봇을 완전히 대체하고, 사용자가 검사명을 정확히 모르더라도 자연어로 질문하면 의도와 조건을 파악해 SCL의 공식 검사 DB·FAQ·공문·홈페이지 문서를 검색하고, 근거 있는 답변과 후속 행동까지 제공하는 실서비스형 LLM·RAG 챗봇을 구축한다.

서비스 가칭은 **SCL AI 검사정보 도우미** 또는 **SCL 검사 업무 코파일럿**이 적절하다.

단순히 “자유롭게 대화하는 챗봇”이 아니라 다음 세 가지를 결합해야 한다.

1. 자연어 이해와 대화
2. 검사정보 검색·비교·정리
3. 문의 접수·상담원 연결 등 후속 처리

## 2. 기존 챗봇의 문제 정의

| 기존 챗봇 | 발생하는 문제 | 발전 방향 |
|---|---|---|
| 버튼을 순서대로 선택 | 사용자가 메뉴 구조를 이해해야 함 | 자유입력 중심 |
| 정해진 시나리오만 지원 | 표현이 조금만 달라도 대응 불가 | 의도·조건·동의어 이해 |
| 검사명을 알아야 검색 가능 | 정확한 검사명을 모르면 탐색 어려움 | 질환·검체·목적 기반 검색 |
| 정적인 안내문 제공 | 여러 정보를 다시 찾아봐야 함 | 정보를 모아 요약 제공 |
| 대부분 링크·전화번호 안내 | 사용자가 다시 설명해야 함 | 문의 내용 정리 및 전달 |
| 문맥 기억 없음 | “그 검사는?” 같은 후속 질문 불가 | 세션 단위 대화 기억 |
| 답변 불가 시 막힘 | 홈페이지 이탈 또는 전화 문의 | 추가 질문 후 상담 전환 |

핵심 문제는 질문 종류가 적다는 것보다, **사용자가 챗봇 구조에 맞춰 질문해야 한다는 것**이다.

## 3. FAQ에서 확인된 실제 문의 특성

[SCL 공개 FAQ](https://www.scllab.co.kr/front/bbsList.do?bbsId=BBS_0014&webMode=FRONT&searchOp6=)는 총 14건이며, 다음 유형으로 구성되어 있다.

- 관련 검사항목 추천
- 검사 전 식사·채혈 가능 여부
- 검체 용기 및 채혈 순서
- 검체 보관·운송 조건
- 검체 전처리 방법
- 참고치와 검사 원리
- 검사결과 표현의 의미
- 검사 적정 채혈 시기
- 원격지원 방법

예시:

- “골다공증 관련 검사는 어떤 검사가 있나요?”
- “HbA1C 검사 시 식후에 채혈해도 가능한가요?”
- “Blood culture 전용용기는 어떻게 보관하나요?”
- “잠복결핵 검사 전용용기 채혈순서는?”
- “Microalbumin random urine 결과는 어떻게 해석하나요?”

따라서 챗봇은 홈페이지 페이지를 찾아주는 수준을 넘어, **검사 전·중·후 실무 질문에 공식 근거를 바탕으로 답하는 구조**가 되어야 한다.

## 6. 핵심 기능

### 6.1 자연어 검사 검색

검사명 일치 검색이 아니라 조건 기반 검색을 제공한다.

> “혈액으로 하는 갑상선 검사 알려줘.”  
> “소변으로 하는 마약 검사 찾아줘.”  
> “혈액검사 중 결과가 빨리 나오는 것만 보여줘.”  
> “골다공증 관련 검사 중 소요일 3일 이내인 것 알려줘.”

처리 과정:

```text
질문 분석
→ 질환·검체·소요일 등의 조건 추출
→ 검사 DB 필터링
→ 의미 유사도 기반 후보 검색
→ 조건에 맞는 검사 비교
→ 출처와 상세페이지 제공
```

결과가 여러 개라면 표로 비교한다.

| 검사명 | 검체 | 검사방법 | 검사일 | 소요일 |
|---|---|---|---|---|

### 6.2 오타·약어·동의어 처리

다음을 같은 개념으로 연결할 수 있어야 한다.

- HPV / 인유두종바이러스
- HbA1c / 당화혈색소
- 갑상선 기능검사 / TFT
- 혈액 / 전혈 / 혈청 / 혈장
- 소변 / urine
- 잠복결핵 / IGRA / QuantiFERON

검사 도메인 사전과 임베딩 검색을 함께 사용한다.

### 6.3 복합 질문 처리

> “HPV 검사 검체랑 용기, 소요일 같이 알려줘.”

검사명이 충분히 구체적이면 모든 요청을 한 번에 답한다. HPV 검사처럼 여러 종류가 있어 답이 달라질 경우에만 추가 질문한다.

> “HPV DNA 검사와 HPV genotype 검사 중 어떤 검사를 찾으시나요?”

즉, **무조건 되묻는 것이 아니라 답변에 영향을 주는 모호함이 있을 때만 질문**한다.

### 6.4 대화 문맥 기억

같은 세션에서는 앞에서 선택한 검사와 조건을 기억한다.

```text
사용자: HPV 검사 알려줘
챗봇: 관련 검사 3개를 찾았습니다
사용자: 그중 첫 번째는 어떤 용기를 써?
챗봇: 첫 번째 검사인 ○○검사는 △△용기를 사용합니다
사용자: 소요일도 알려줘
```

개인정보 문제가 있으므로 기본적으로 세션 종료 후 문맥은 폐기한다. 장기 대화 기록은 로그인과 별도 동의가 있을 때만 고려한다.

### 6.5 답변과 근거 제공

답변 형식은 다음을 기본으로 한다.

1. 짧은 결론
2. 검사 또는 업무정보
3. 주의사항
4. 출처와 정보 기준일
5. 다음 행동 버튼

```text
HbA1C 검사는 식후에도 채혈할 수 있습니다.

이 검사는 통상적으로 최근 2~3개월의 평균 혈당 농도를
반영하기 때문에 식후 채혈이 가능합니다.

출처: SCL 자주하는 질문
정보 기준일: 2026-08-15

[검사 상세보기] [관련 검사 찾기] [상담 문의]
```

### 6.6 페이지·문서 검색과 요약

정보가 여러 페이지나 공문에 흩어져 있으면 한 번에 정리한다.

> “이번 연휴 검사 일정 변경사항만 요약해줘.”  
> “최근 새로 추가된 분자진단 검사 알려줘.”

답변에는 원문 링크를 반드시 제공한다.

### 6.7 상담원 및 문의 접수

답을 못 찾았다고 바로 전화번호만 보여주지 않는다.

```text
검색 결과 없음
→ 추가 정보 질문
→ 다시 검색
→ 여전히 근거 없음
→ 상담 가능 시간 확인
→ 상담원 연결 또는 문의 접수
```

상담원에게는 다음 정보를 전달한다.

- 사용자의 원래 질문
- 챗봇이 확인한 조건
- 검색한 자료
- 제공한 답변
- 해결되지 않은 부분
- 대화 요약

야간·주말에는 문의를 접수하고 접수번호와 예상 응답 방식을 안내한다.

## 7. 외부 웹 검색 원칙

“사이트에 없으면 인터넷 검색”은 가능하지만, 의료·검사정보이므로 일반 검색 결과를 바로 답변으로 사용하면 위험하다.

추천 우선순위는 다음과 같다.

1. SCL 검사 DB
2. SCL 공식 FAQ·공문·문서
3. SCL 홈페이지
4. 사전에 승인된 외부 기관
5. 상담원 연결

승인 가능한 외부 출처 예시:

- 질병관리청
- 식품의약품안전처
- 건강보험심사평가원
- 보건복지부
- 관련 전문학회 및 공식 가이드라인

블로그·카페·광고성 콘텐츠는 검사 답변의 근거로 사용하지 않는다. 외부 출처를 사용한 답변은 SCL 공식 정보와 명확하게 구분해야 한다.

## 8. 답변 금지 및 안전 원칙

### 답변 가능

- 검사 목적과 일반적 설명
- 검체·용기·채취·보관 방법
- 검사일·소요일
- 공식 FAQ에 있는 결과 표현 설명
- 의뢰·결과 확인 방법
- 공식 페이지·문서 안내

### 제한 또는 상담 전환

- 개인 검사결과를 통한 진단
- 치료방법이나 약물 추천
- 응급 여부 판단
- SCL 공식 정보와 외부 정보가 충돌하는 경우
- 환자정보 수정·검사 취소 등 권한이 필요한 업무
- 홈페이지와 승인 자료에서 근거를 찾지 못한 답변

근거가 없으면 “일반적으로는”이라는 표현으로 답을 만들어내지 않고, 명확하게 확인 불가 상태를 알려야 한다.

## 9. 데이터 및 RAG 설계

“사이트 전체를 크롤링해서 벡터 DB에 넣는 것”만으로는 부족하다. 데이터 성격에 따라 나눠야 한다.

| 데이터 | 처리 방식 |
|---|---|
| 검사코드·검체·소요일·검사일 | 구조화 DB 검색 |
| 검사명·질환·동의어 | 키워드+벡터 하이브리드 검색 |
| FAQ·안내서·공문 | RAG 문서 검색 |
| 담당 부서·연락처 | 구조화 DB |
| 로그인 결과·접수 상태 | 내부 API |
| 외부 의료정보 | 승인 도메인 검색 |

### 데이터 확보 전략

- 초기 개발: 홈페이지 크롤링과 자체 DB 구축
- 실서비스 전환: 회사의 검사 DB 또는 API 연동
- 변경사항: 자동 수집 및 재색인
- 문서마다 등록일·수정일·출처·URL 저장
- 변경된 검사정보는 기존 데이터와 버전 비교
- 오래된 정보는 답변에서 제외하거나 경고 표시

크롤링은 초기 구축에는 가능하지만, 실서비스의 핵심 검사정보는 장기적으로 공식 DB 연동이 필요하다.

## 10. 서비스 처리 구조

```text
사용자 질문
    ↓
오타·약어·동의어 정규화
    ↓
의도와 조건 추출
    ↓
검사 DB 검색 + 문서 RAG
    ↓
답변 가능 여부와 근거 검증
    ↓
LLM 답변 생성
    ↓
출처·기준일·다음 행동 제공
    ↓
미해결 시 상담원 또는 문의 접수
```

LLM이 검사정보를 기억해서 답하는 구조가 아니라, **검색된 공식 데이터를 읽기 쉽게 정리하는 역할**을 맡아야 한다.

## 12. 성공 지표

전화 문의 감소 목표가 30%와 50%로 혼재되어 있으므로 다음처럼 정리한다.

### 핵심 KPI

| 지표 | 목표 |
|---|---:|
| 전화 문의 감소 | 1차 30%, 도전 목표 50% |
| 단순 문의 자동 해결률 | 80% 이상 |
| 검사항목 검색 성공률 | 85% 이상 |
| 야간·주말 인스코프 문의 자동 처리율 | 70% 이상 |
| 평균 문의 해결시간 | 기존 대비 50% 감소 |

### 품질 가드레일

- 구조화된 검사정보 필드 오류: 배포 검증에서 0건
- 출처 없는 의료·검사 답변: 0건
- 개인정보 노출 사고: 0건
- 답변 불가 질문 수집률: 100%
- 상담원 전환 시 대화 요약 전달률: 100%

현재 문의량을 모르기 때문에 출시 전에 최소 2~4주간 전화 문의량·유형·평균 처리시간을 측정해야 감소율을 계산할 수 있다.

핵심 방향은 이거야.

```text
현재 SCL 홈페이지 UI
→ 백엔드 API
→ 개인정보·욕설·공격 입력 검사

→ 스트리밍 답변
→ 상담 전환·미해결 질문 기록
```

OpenAI의 Structured Outputs로 질문을 정해진 의도·조건 구조로 변환하고, [File Search](https://developers.openai.com/api/docs/guides/tools-file-search)로 SCL 공개 문서를 검색하게 만들 수 있어. 같은 세션의 후속 질문도 [대화 상태 관리](https://developers.openai.com/api/docs/guides/conversation-state) 방식으로 처리한다. 입력·출력 안전성은 자체 개인정보 필터와 [OpenAI Moderation](https://developers.openai.com/api/docs/guides/moderation)을 함께 적용한다.

구현 순서는 다음과 같다.

1. FastAPI 백엔드와 `/api/chat` 생성
2. OpenAI Responses API 연결
3. 기존 홈페이지 챗봇을 실제 API에 연결
4. 의도·조건 추출과 후속 질문 구현
5. 샘플 검사 JSON 검색과 공개문서 RAG
6. 욕설·개인정보·프롬프트 공격 방어
7. 상담 전환·피드백·미해결 질문 기록
